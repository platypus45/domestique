Findings, worst first

  1. Two files are half the codebase structure

    app.py and training_planner.py together hold 36,781 of 79,050 lines. They also hold 23,851 of the 39,856 lines that live in oversized functions — so the size problem and the module problem are the same problem.

    app.py 20,960 lines 36 imports 3 importers training_planner.py 15,821 lines 14 imports 8 importers everything else 42,269 lines across 60 modules

    A module that imports 36 of its own siblings has no boundary left to defend; anything may reach anything. That is what makes a change here cost a full-suite run to be sure of.

    FixKeep extracting leaves, as with hr.py, routes_lib.py, search_lib.py. The blocker is named below (finding 06) and is worth clearing first: it gates roughly 725 further lines.

  3. 9,648 lines of domain logic are reachable only through HTTP separation

    148 route handlers. 68 are longer than 40 lines. A handler's job is to parse the request, call one domain function, and serialise the answer; past that, the logic cannot be reused by the CLI, the scheduler or a test without a Flask test client.

    432 lines api_plan_generate also touches: filesystem 312 lines setup_save also touches: filesystem 300 lines api_plan_auto_adjust also touches: filesystem + SQL 297 lines api_rider_stats also touches: SQL 288 lines api_weekly_plan also touches: filesystem 284 lines api_week_summary 218 lines api_routes_suggest

    Five handlers reach SQL directly rather than through a repository call, so the request shape and the table shape are coupled with nothing in between.

    FixFor each handler over ~80 lines, lift the body to a plain function taking plain arguments and returning plain data. The handler keeps request parsing and the HTTP status. Start with api_plan_generate — it is the one you press.
  4. A 24-parameter signature that five call sites reconstruct by hand coupling

    sample_week_workouts takes 24 parameters. They are not 24 things — they are four objects, unpacked, and all four already exist:

    the week 7 WeekContext + IntensityBudget the athlete 6 Goal the plan 9 PlanState per-call 2 emphasis_profile, block_focus -- 24 -> sample_week_workouts(ctx, state)

    expand_blueprint_week is the pure form of it: it takes goal and five attributes of goal. Across the module, 84 argument lines are literally x=goal.x, and the two builders alone cost 165 lines of argument threading across 9 call sites.

    This is not cosmetic. It is the mechanism by which the five entry points drifted: each reassembles those 24 arguments by hand, and they stopped agreeing. That is why a 40-rider sweep found back-to-back hard days in regenerate and nowhere else.

    FixPass the reference instead of unpacking 99% of the object's attributes. Nothing new needs building — WeekContext, PlanState, Goal and IntensityBudget are all already there. Step 1 of notes/planner-cleanup-plan.md.
  5. A duplicated rule whose only enforcement is a comment duplication

    _np_fraction_from_samples exists in both app.py and training_planner.py. Verified by AST comparison with docstrings stripped: the code bodies are identical. The docstring says so itself, and asks a human to keep it that way.

    app.py:5359 "Byte-identical to the planner's training_planner._np_fraction_from_samples — the two scanners must stay in lockstep." nothing checks this.

    Normalised power feeds TSS, which feeds every budget in the planner. If the two drift, planned load and ridden load are quietly in different units. Nine duplicate-shape groups exist in all; this and _build_daily_load_series (oos_validation / tau_fitting) are the two that cross a module boundary.

    FixOne definition in a leaf module both already import — zones.py is the natural home. If deduplicating is deferred, the cheap stopgap is a test asserting the two AST bodies are equal, which turns the comment into a gate.
  6. Seven import cycles, one of them load-bearing coupling
    app <-> training_planner app <-> icu_calendar_push db <-> profile_manager db <-> training power_curve <-> ride_storage profile_manager<-> training_planner training_planner <-> week_plan (deliberate: lazy import inside methods)

    A cycle means neither module can be imported, read or tested alone, and it is why extracting from app.py keeps needing a deferred import to break the loop. The app ↔ training_planner one is the expensive one.

    FixEach cycle resolves by moving the shared thing to a leaf. db ↔ profile_manager and db ↔ training both look like a path or config value that belongs in paths.py/config.py.
  7. Forty module globals rebound at runtime; ten by more than one function state

    A global rebound from several places is state with no owner — the same shape of defect as the session-state problem just fixed in the planner.

    app.py _icu_push_timer rebound by 3 functions db.py _sync_thread rebound by 3 db.py _sync_stop rebound by 3 app.py WORKOUT_DIR rebound by 2 (_apply_profile_paths, setup_save) app.py GPX_DIR rebound by 2 db.py _auth_disabled / _consecutive_failures / _last_sync_error rebound by 2 each

    WORKOUT_DIR and GPX_DIR are the known hazard, already pinned by test_profile_path_rebinding.py: any module that does from app import WORKOUT_DIR binds the value and silently serves the previous profile's library after a switch. The db.py sync-thread trio is unguarded and is touched from a background thread.

    FixThe three db.py sync globals are one object's fields — a small SyncState with the thread, the stop flag and the failure counters, owned by start/stop.
  8. Dead code: one unreachable block, twenty-five unreferenced functions cleanup

    The 141-line unreachable block in regenerate_from_today is the legacy builder left stranded when that path moved onto the owner — mine, and deleted.

    The other 25 are pre-existing and are reported, not touched, per the project's own rule about not deleting unrelated dead code. Worth a look: sleep.py:compute_sleep_score, ride_report_png.py:render_ride_report_png, training.py:classify_acwr / classify_monotony / classify_ramp — three classifiers with no caller, in a package whose value is its science.

    FixConfirm each against the UI before deleting; a couple may be reached by name from a template or a config string, which the detector cannot see.
  9. In progress, currently switched off: the single week owner not landed

    week_plan.TrainingWeek exists and works: one method writes session state, constraints are consulted before a slot is committed, and plan-level policies are re-committed through the same door by finish() so none can win by running last. Against the six rules in plan_invariants.py it is a clear improvement.

    40 riders x 5 entry points legacy owner hard-day spacing breaches 5 0 weekly-volume breaches 51 weeks, max +104% 0 weeks over 1.15x target 5% 0%

    Switching it on cost 19 test failures, because the legacy loop carried two dozen behaviours the invariants say nothing about. Nine have since been carried across — block focus and the blueprint modes, athlete-owned and race session immutability, the per-type ceiling, the taper exemption, the novelty window and HIT-rotation trim, priority commit ordering, a per-slot budget reserve. 19 failures down to 6.

    All six trace to one defect: slot type and served content are different things, and the library can answer an endurance slot with a threshold file. Patching it after the fact was tried and measured — it took the failures from 6 to 12, because an unmatched slot is refilled elsewhere and the breach relocates. It belongs where match_zwo chooses.

    The lesson is about the evidence, not the code. Six invariants coming back clean across 40 riders says those six rules hold — it is not evidence that the plans are right. It was reported here as stronger than it was.

    FixOne defect stands between this and switching on: step 4 of notes/planner-cleanup-plan.md.
